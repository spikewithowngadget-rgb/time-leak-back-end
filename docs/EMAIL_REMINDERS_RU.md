# Email-напоминания TimeLeak

Система отправляет письма о будущих заметках независимо от того, открыт ли
браузер или мобильное приложение. По умолчанию письмо приходит ежедневно
за **3, 2 и 1 день**, в **09:00 Asia/Almaty**. В сам день заметки и после её
даты письма не отправляются. Для повторяющихся заметок учитывается дата
каждого следующего повтора.

Доработка backend для этих напоминаний отдельно разрешена пользователем.
Предыдущее ограничение «только фронтенд» относится к прошлому этапу и не
описывает этот релиз. При этом существующие Flutter auth/notes-контракты,
идентификаторы заметок, файлы и данные пользователей сохраняются.

## Получатели и подтверждение почты

Письма получают только активные пользователи с отдельным подтверждённым
email-контактом и включёнными напоминаниями. Поле `users.email` не меняется:
телефонная авторизация и мобильные аккаунты работают как раньше. Псевдоадреса
телефонных аккаунтов не используются для рассылки.

В веб-приложении настройка находится на странице «О приложении». Поток API:

1. С пользовательским Bearer вызвать `GET /api/v1/auth/email-reminders`. Если
   почта не задана, ответ содержит пустой email, `verified_at: null`,
   `enabled: false`.
2. Запросить код через существующий `POST /api/v1/auth/email-otp/request`
   с `{email}`. Код доставляет Resend; его ключ остаётся на сервере.
3. Передать код непосредственно в `POST /api/v1/auth/email-reminders/verify`
   с `{request_id, code, enabled, language}` и пользовательским Bearer.
   Отдельный `/email-otp/verify` здесь не нужен: он потребляет код.
4. Изменить состояние через `PUT /api/v1/auth/email-reminders` с обязательным
   `{enabled}` и необязательным `language`. Включение требует ранее
   подтверждённой почты; отключение без контакта идемпотентно.

Email берётся только из проверенной OTP-записи, пользователь — из Bearer uid.
Клиент не может передать другой `user_id` или произвольный email на шаге
подтверждения. Код одноразовый, ограничен сроком действия и числом попыток.
Отсутствующий `enabled` при подтверждении означает `false`. Подтверждение
контакта и сохранение настроек не являются командами немедленной отправки
напоминания. Эти маршруты не создают email-вход, JWT или объединение аккаунтов.

Ответ контакта содержит только `{email, verified_at, enabled, language}`;
`user_id` не возвращается. Ответы не кэшируются. Администраторские методы
недоступны с пользовательским токеном.

## Управление в админке

Открыть `/admin/dashboard#settings` → «Напоминания по email».

| Поле | Допустимые значения | По умолчанию |
| --- | --- | --- |
| Включено глобально | `true` / `false` | `true` |
| `days_before` | целое 1–30, пресеты 1/3/7/14/30 | 3 |
| `send_hour` | целое 0–23 | 9 |
| `timezone` | валидный IANA, без `Local` | `Asia/Almaty` |

Горизонт N означает ежедневное письмо за N, N−1, …, 1 день, а не одну
отправку ровно за N дней. Можно сохранить настройки с отключённой отправкой.
Изменения применяются планировщиком; кнопки ручной рассылки нет.

- `GET /api/v1/admin/reminders/settings` — текущие значения и метаданные
  `revision`, `updated_at`.
- `PUT /api/v1/admin/reminders/settings` — четыре обязательных редактируемых
  поля: `enabled`, `days_before`, `send_hour`, `timezone`. Неизвестные поля,
  неполное тело, недопустимые диапазоны и часовой пояс дают 400.
- `GET /api/v1/admin/reminders/status` — только агрегированные данные:
  `sender_configured`, `verified_contacts`, `pending`, `sent`, `failed`,
  `cancelled`, `last_run_at`, `next_run_at`, `last_sent_at`.

`verified_contacts` считает активные подтверждённые контакты с включёнными
письмами. Статус не содержит адресов, заголовков заметок или секретов.
`sender_configured` подтверждает наличие корректной конфигурации отправителя;
сам по себе он не доказывает доставку письма или верификацию домена в Resend.
Админка переведена на казахский, русский и английский.

## Языки и содержание писем

Шаблоны HTML и обычного текста поддерживают 11 языков:
`kk`, `ru`, `en`, `zh`, `hi`, `fr`, `de`, `es`, `it`, `pt`, `ar`.
`kz` нормализуется в `kk`; региональные варианты сводятся к базовому языку.
Неизвестный язык использует английский. Пустая настройка контакта использует
язык пользователя.

Письмо содержит название заметки, дату события, число оставшихся дней,
ссылку на календарь с выбранной датой и ссылку управления напоминаниями.
Пользовательский текст экранируется в HTML; тема очищается от управляющих
символов. Арабский шаблон использует RTL. Файлы заметок и их приватные URL
не прикладываются к письмам.

## Планировщик и повторные попытки

`ReminderService.Run` запускается вместе с API и завершается по его контексту.
Проверка выполняется при запуске и затем каждую минуту. До указанного часа
письма не отправляются. После часа отправки допустима обработка ещё не
выполненной очереди текущего локального дня; пропущенные прошедшие дни
не догоняются. Сравниваются календарные даты в настроенном часовом поясе.

Очередь хранится в SQLite. Уникальность определяется сочетанием пользователя,
заметки, даты повтора и количества дней до неё. Перезапуск API не создаёт
новое письмо для того же события. Перед отправкой повторно проверяются
контакт, состояние пользователя, существование/актуальность заметки и
глобальные настройки. Удалённые, завершённые одноразовые или утратившие
актуальность задания отменяются. Задания получают ограниченную аренду;
результат записывается по токену этой аренды.

Resend получает `Idempotency-Key: timeleak-reminder/{delivery_id}`. При повторах
сохраняются тот же ключ и неизменный текст/HTML/тема/получатель. Провайдер
хранит ключи 24 часа; локальное окно повторов ограничено 20 часами и текущим
днём, то есть меньше окна провайдера. [Документация Resend об идемпотентности](https://resend.com/docs/dashboard/emails/idempotency-keys).

Временные сетевые ошибки, 408, 429, 5xx и конфликт одновременно выполняемого
идемпотентного запроса допускают повтор с задержкой. Учитывается
`Retry-After`, число попыток ограничено восемью. Постоянные ошибки авторизации
или некорректного запроса фиксируются как ошибка без бесконечного цикла.
Обработка ограничена пакетами; между запросами напоминаний выдерживается
пауза в одну секунду. OTP-письма используют тот же лимит команды Resend.

На дату проверки документации 4 ноября 2026 года Resend указывает базовый
лимит 10 запросов в секунду на команду для всех её API-ключей. Реальный лимит
и квоты зависят от настроек команды; ответ 429 и заголовки провайдера имеют
приоритет перед предположениями приложения. [Официальные лимиты Resend](https://resend.com/docs/api-reference/rate-limit).

## Конфигурация и совместимость

Используются существующие защищённые настройки `RESEND_API_KEY`,
`RESEND_FROM_EMAIL`, `RESEND_FROM_NAME`. Секреты не передаются в браузер,
OpenAPI, логи или админский статус. Отправитель и его домен должны быть
разрешены в Resend. Для планировщика не требуются FFmpeg, cron или открытая
вкладка браузера.

Миграция `0023_email_reminders.sql` добавляет только новые таблицы:
`email_reminder_settings`, `user_email_reminder_contacts`,
`email_reminder_deliveries` и их индексы. Старые миграции не редактируются.
Заметки, пользователи и их файлы не переписываются. Дефолтный глобальный
режим включён, но из старых аккаунтов автоматически не создаются контакты:
без отдельного подтверждения и включения email-напоминания не отправляются.

## Проверка, сборка и обновление

До публикации выполнить из соответствующих проектов:

```sh
# time-leak-back-end
 go test ./...
 CGO_ENABLED=1 go build -o <STAGING>/timeleak-api ./cmd

# time-leak-admin
 go test ./...
 cd client
 npm test
 npm run build
```

Backend использует `mattn/go-sqlite3`, поэтому его собирают с CGO на Linux
нужной архитектуры и с C-компилятором. Сборка `CGO_ENABLED=0` для API не
подходит. Статические файлы веба можно собрать локально; Node на production
для готового артефакта не нужен. Стенд проверки должен использовать отдельную
БД и подставной Resend, чтобы тесты не рассылали письма пользователям.

Перед обновлением сделать согласованную резервную копию SQLite через
SQLite backup API с учётом WAL, сохранить текущий исполняемый файл и unit.
Собирать новый релиз отдельно от production checkout; сохранить рабочий
каталог и защищённое окружение API, чтобы относительные пути БД/файлов не
изменились. Проверить существующие Flutter auth/notes сценарии на стенде.
После разрешённой активации нового API миграция применяется при его запуске.
Подробный порядок публикации фиксируется в документации конкретного релиза.

При откате предпочтительно вернуть предыдущий исполняемый файл, сохранив
добавленные таблицы и новые пользовательские записи. Восстановление старого
снимка БД может потерять заметки, созданные после снимка, и требует отдельной
оценки. Этот документ не является подтверждением публикации.

В baseline `cmd/main.go` присутствует ранее существовавший Swagger seed с
известными тестовыми реквизитами. Это отдельная найденная проблема, а не
функция напоминаний; данный релиз её автоматически не устраняет. При
перезапуске нельзя считать этот риск исправленным без отдельной проверки.

## Исходники и проверки контрактов

- `internal/domain/reminders.go` — модели и валидация глобальных настроек.
- `internal/repository/reminders.go`, `email_reminder_contact.go` — очередь и контакты.
- `internal/service/reminder_service.go` — расписание, повторная проверка, retry.
- `internal/service/reminder_message.go` — 11 языков, HTML и обычный текст.
- `internal/service/resend_reminders.go` — Resend и idempotency key.
- `internal/handler/email_reminder_contact.go`, `reminder_admin.go` — маршруты.
- `internal/handler/openapi.json` — все шесть новых операций и схемы.
- `time-leak-admin/web/assets/js/reminders.js` — глобальные настройки в админке.

Отдельные проверки админских маршрутов и OpenAPI прошли: запрет гостевого/
пользовательского доступа, разрешение admin, диапазоны и IANA, пресеты,
ошибки без утечки данных. DOM-тест админки проверяет загрузку, явное сохранение,
отсутствие автоматической отправки/сохранения при редактировании, отклонение
31 дня и переключение языка. Полный результат тестов и статус публикации
должны фиксироваться при завершении релиза.
